# TASK-001: Reference-Driven UI Delivery Implementation Plan

## Current Behavior

- The public catalog contains exactly 18 commands. One command spawns one matching isolated agent, that agent invokes one Skill, reports evidence, and stops.
- `ui-designer` can write `tasks/TASK-NNN/ui-design.md` and confirmed `specs/ui-design.md`, but it has no machine-readable way to map visual references to surfaces, states, viewports, anchors, or tolerances.
- `writing-plans` and `coder` do not consume a shared reference contract. `coder` has no explicit correction-iteration contract for preserving cases that already passed.
- `browser-verify` runs the project Doctor, uses the project-owned `toolchain/bin/agent-browser.mjs`, and reports browser evidence, but it has no reference mode, append-only evidence layout, cross-iteration finding classification, or reference-specific verdict rules.
- `verify` runs existing application checks and does not know whether a reference-aware task has a current Browser Verify `PASS`.
- The pinned `agent-browser@0.32.3` already supports the required browser primitives: explicit sessions, `set viewport`, selector-scoped screenshots (`screenshot [selector] [path]`), scoped screenshot diffs (`diff screenshot --baseline ... --selector ... --output ... --threshold ...`), accessibility snapshots, reduced-motion emulation, console/errors/network inspection, and JSON output. No new browser provider or application dependency is required.
- `.claude/` is canonical. `.agents/skills/` and `.agents/codex-agents.toml` are generated by `npm run sync:agents` and must not be edited by hand.

## Intended Behavior

Reference-aware work continues through the existing Manual Flow:

```text
user -> ui-designer (when interpretation is needed) -> STOP
user -> writing-plans (when a file-level handoff is useful) -> STOP
user -> coder -> STOP
user -> browser-verify -> PASS | FAIL | BLOCKED | NOT-APPLICABLE -> STOP
user -> coder or debugger (only when explicitly selected) -> STOP
user -> browser-verify -> STOP
user -> verify -> STOP
```

The roles exchange one task-level Reference UI Contract. UI Designer remains planning-only, Coder remains the only production-code owner, Browser Verify remains verification-only and may write only task evidence, and Verify remains a project-check verdict rather than a visual comparator. No role invokes another role, no automatic retry loop is added, and the command catalog and transition graph remain unchanged.

## Preconditions And Confirmed Decisions

1. The Repository Root and Application Root for this toolset change are both the repository root.
2. `tasks/TASK-001/requirements.md` is the confirmed feature specification.
3. No new public command, agent, Skill, orchestrator, workflow lane, or transition is allowed.
4. The Reference UI Contract is task data, not a Living Specification. Failed iterations, screenshots, diffs, measurements, and remote captures remain under the Task Workspace and are excluded from the published package by the existing `package.json#files` allowlist.
5. A visual source URL is metadata, not a stable baseline. Every required visual case must resolve to a readable local baseline artifact before a reference verdict can be produced.
6. Browser readiness continues to come only from `toolchain/bin/doctor.mjs --json`. Reference artifact validation must not become a second Doctor.
7. Browser actions continue to go only through `toolchain/bin/agent-browser.mjs`; the internal Reference UI artifact helper described below validates and finalizes task files but is not a second browser interface.
8. The existing `agent-browser@0.32.3` pin is sufficient. Do not change `toolchain/manifest.json`, `package.json` dependencies, or application dependencies unless an implementation test disproves the locally verified command support.
9. The Common Browser Verify rules must define and test one conservative default acceptance policy. Use the pinned CLI color threshold (`0.1`) and a maximum whole-surface mismatch ratio of `0.01` unless a manifest or Project Ruleset supplies a stricter value. High-priority regions remain hard gates at their declared tolerance; semantic, interaction, accessibility, console, and network failures are never averaged into a visual score.
10. Phase boundaries below are verification gates, not automatic steps or required commit boundaries. The user explicitly starts every later Coder, Browser Verify, Verify, or Docs Generator invocation.

## Reference UI Contract

Use this task layout in installed projects:

```text
tasks/TASK-NNN/reference-ui/
|-- manifest.json
|-- references/                         # local baselines or captured remote references
|-- .staging/<owned-session>/           # current Browser Verify run only
`-- validation/
    |-- iteration-001/
    |   |-- evidence.json
    |   `-- cases/<case-id>/
    |       |-- current.png
    |       |-- diff.png
    |       `-- regions/<region-id>/
    |           |-- current.png
    |           `-- diff.png
    `-- iteration-002/
        `-- ...
```

### Manifest contract

`manifest.json` is versioned and machine-readable. Its required top-level fields are:

- `schemaVersion`, `taskId`, `manifestVersion`, and repository-relative `applicationRoot`;
- `cases`, with stable case IDs and a required/optional flag;
- `acceptancePolicy`, including visual threshold and mismatch-ratio defaults or explicit inheritance from the Common/Project rule;
- reference source metadata and a readable local `baselinePath` for every verifiable case.

Each case records:

- target kind (`route` or `component`), target identity, exact route when applicable, and required user-visible state;
- viewport width, height, CSS scale, theme, and locale when relevant;
- priority, named visual regions, stable locator strategy, and per-region tolerance overrides;
- deterministic setup/interactions and observable semantic outcomes;
- dynamic regions and whether each is asserted semantically, compared through a stable scoped region, or excluded only from the pixel verdict;
- allowed deviations with reasons, including accessibility or established product constraints.

The validator rejects unknown schema versions, duplicate IDs, missing routes/states/viewports, contradictory cases, path traversal, unreadable baselines, remote references without a captured baseline, invalid tolerances, and unsupported locator/action types. A manifest may be revised only by incrementing `manifestVersion`; every evidence iteration records both the version and a content digest.

### Validation evidence contract

Each `validation/iteration-NNN/evidence.json` records:

- schema, task, manifest version/digest, iteration number, exact application URL, owned browser session, and pinned browser capability/version;
- exact route, state, viewport, setup interactions, readiness observations, screenshots, diffs, and measurements for every case;
- separate axes for visual, structural/semantic, behavior, accessibility, console, and network health;
- findings keyed by stable `caseId + regionId + axis`, with severity, expected observation, actual observation, supporting artifact/measurement, and smallest user-visible correction target;
- passed cases and `new`, `resolved`, `unchanged`, and `regressed` findings relative to the latest compatible prior iteration;
- final `PASS`, `FAIL`, `BLOCKED`, or `NOT-APPLICABLE` verdict and the reason for every non-pass outcome.

The finalizer writes one new iteration atomically and fails if that iteration path already exists. It never updates a baseline, manifest, earlier iteration, application source, tests, configuration, fixtures, or application data.

## Ordered File Changes

### Phase 1 — Define and validate the task contract

Create:

- `toolchain/schemas/reference-ui-manifest.schema.json` — public machine-readable shape for manifest version 1.
- `toolchain/schemas/reference-validation.schema.json` — public machine-readable shape for validation evidence version 1.

- `toolchain/bin/reference-ui.mjs` — internal artifact CLI with `validate-manifest` and `finalize-validation` operations. It must not launch a browser, server, command, agent, or Skill.

### Phase 4 — Add Browser Verify reference mode and evidence-only authority

Modify canonical policy:

- `.claude/skills/browser-verify/SKILL.md` — activate reference mode only from an explicit manifest or explicit reference-verification request; retain ordinary mode unchanged when no reference surface exists.
- `.claude/agents/browser-verify.md` — permit `Write(tasks/**)` and `Edit(tasks/**)` only for reference evidence/drafts, keep production/test/config/data edits forbidden, and keep the existing Browser Verify transitions and STOP boundary.
- `.claude/commands/browser-verify.md` — describe reference evidence without changing the command name, spawned agent, phase, or transitions.
- `rulesets/common/browser-verify/rules/reference-conformance.md` — define deterministic capture, the conservative default tolerance, named-region hard gates, dynamic-region handling, finding shape, and baseline immutability.
- `rulesets/common/browser-verify/INDEX.md` — route the new Common rule.

Reference-mode procedure to encode in the Skill:

1. Run project Doctor and stop `BLOCKED` on the existing blocking states.
2. Validate the manifest through `toolchain/bin/reference-ui.mjs`; do not treat it as browser readiness.
3. Require a supplied/emitted application URL and retain existing server approval/ownership rules.
4. Create a unique owned session and staging directory. The first browser command remains `open <exact URL>`.
5. For each required case, use the declared viewport/theme/locale, set reduced motion, reproduce state through approved fixtures or stable semantic interactions, wait for declared readiness plus relevant fonts/images, and capture an interactive accessibility snapshot.
6. Verify semantic/interaction/accessibility requirements independently of pixels.
7. Capture whole-surface and named-region screenshots, then run the pinned screenshot diff using the case/region tolerance. Dynamic exclusions affect only the declared pixel region.
8. Collect exact console, page-error, network, focus, keyboard, responsive, and long-content evidence applicable to the case.
9. Build structured findings and finalize a new append-only iteration atomically. Never alter baselines or prior evidence.
10. Close only the owned session and server, return the four-state verdict with exact evidence paths, recommend one contextual next command, and stop.

Modify tests:

- `test/contracts.test.mjs` — keep `code-reviewer` and `verify` fully read-only; allow Browser Verify only task-scoped evidence writes and assert explicit production immutability, Doctor/adapter ownership, four verdicts, manual next-step semantics, and STOP.

## Essential Tests

1. Manifest and evidence schemas accept their canonical templates and reject unsupported or ambiguous contracts.
2. Task-path confinement prevents source/config writes and path traversal; evidence iterations are append-only.
3. UI Designer, Coder, Browser Verify, and Verify authority boundaries are enforced by contract tests.
4. Catalog tests keep exactly 18 names, one-to-one mappings, existing transitions, and explicit STOP semantics.
5. Browser adapter tests prove exact owned-session forwarding for viewport, screenshot, selector screenshot, and diff commands.
6. Verdict tests keep visual, semantic, behavior, accessibility, console, and network axes separate and enforce hard gates.
7. Cross-iteration tests classify new, resolved, unchanged, and regressed findings by stable identity.
8. Fixture acceptance proves `FAIL -> PASS`, a deliberate regression, semantic interaction coverage, dynamic-region handling, and declared desktop/mobile cases.
9. Mirror tests prove canonical/mirror parity after generation.
10. Full repository checks and package dry-run pass without adding task evidence to the release payload.

## Additional Risk-Based Tests

- Manifest version changes must not compare findings against incompatible prior evidence.
- Optional cases must not hide failure of required cases.
- A high whole-page score must not hide an out-of-tolerance high-priority region.
- Different theme/locale/scale declarations must not share a baseline accidentally.
- Duplicate iteration attempts and interrupted staging finalization must leave prior evidence intact.
- Windows separators, spaces, Unicode task paths, symlinks/junctions, and case-insensitive paths must not escape the Task Workspace.
- A remote URL without a local capture must return `BLOCKED`, not capture or approve a new baseline silently.
- Browser session close must run after capture/diff failure, while an existing user session/server remains untouched.
- Console/network failures unrelated to the declared scenario must be reported without being silently treated as required failures; scenario-affecting failures remain hard gates.
- Low-level antialiasing differences must use reported tolerance; missing elements, geometry, stable fills, and semantic outcomes remain hard assertions.

## Risks And Rollback

- **Raster instability:** Keep text/dynamic content out of hard pixel equality, use declared thresholds, stable geometry/fills, semantic assertions, and named regions. Report measurements rather than relaxing thresholds.
- **Authority drift:** Browser Verify requires task-scoped evidence writes, so tests must distinguish evidence authority from production-code authority and snapshot the fixture source before/after verification.
- **Hidden orchestration:** The internal artifact CLI may validate/finalize files only. It must never launch roles, Skills, servers, or browsers. The user remains the only actor who selects the next Manual Flow command.
- **Mirror drift:** Change canonical `.claude` files first, regenerate once, and fail `check:agents` on any stale mirror.
- **Baseline mutation:** Finalization fails on collisions, and neither Browser Verify nor tests provide an update-baseline mode.
- **Tool capability drift:** Keep the current pin while its contract tests pass. Any future pin change is an explicit manifest/setup/Doctor change with separate review.

Rollback is additive and local: remove the reference schemas/helper, reference templates/rules, and reference-only Skill branches; regenerate `.agents`; remove fixture tests and the live-test script. Ordinary Manual Flow and ordinary Browser Verify remain intact throughout because reference mode activates only from an explicit contract/request. Never roll back by deleting user task artifacts or rewriting prior validation evidence.
